# Система обработки оборудования (НСИ) — архитектура

Документ описывает целевую архитектуру системы за пределами Этапа 1 и предлагает упрощённую (демо) реализацию.

---

### 1.2 Ключевые принципы

- **Документы вне системы** — храним только URL/ID документа, метаданные, хеш и кэш извлечённого контента (текст, таблицы, изображения).
- **Модель — главная сущность.** Единиц оборудования нет; всё привязано к коду модели.
- **Идемпотентность пайплайнов.** Любой шаг можно перезапустить — старые результаты помечаются версией и сохраняются в истории.
- **Источник всегда виден.** Каждое значение характеристики/ВВ имеет `source = {документ | интернет | аналог | ручной | классификатор}` и `confidence`.
- **Эксперт важнее автомата.** Любое поле можно «зафиксировать экспертом» — оно перестаёт перезаписываться автоматикой.

## 2. Структура данных (сущности)

```ts
// Иерархия (этап 1, реализовано)
HierarchyNode {
  id, parentId?, type: 'enterprise'|'plant'|'workshop'|'site'|'group',
  name, description?, attributes: Record<string,string>
}

// Классификатор (двухуровневый)
ClassDef {
  id, name,                            // нормализовано по п.8.2
  priorityChars: PriorityChar[]        // приоритетные характеристики класса
  subclasses: SubclassDef[]
}
SubclassDef {
  id, name, keywords: string[], patterns: string[],
  priorityChars: PriorityChar[]        // переопределение/доп. на уровне подкласса
}
PriorityChar {
  key,                  // напр. "мощность", "напряжение"
  unit,                 // целевая единица СИ ("кВт")
  type: 'number'|'enum'|'text',
  aliases: string[]     // как может называться в документе
}

// Модель (главная сущность)
EquipmentModel {
  id,
  rawCode, normalizedCode,             // п.8.3
  classId?, subclassId?,
  expertConfirmed: boolean,
  status: 'draft'|'TOR'|'archived',    // ТОР = норм. код + класс + подкласс
  hierarchyNodeIds: string[],          // в каких узлах используется

  documents: DocumentRef[],            // ссылки на паспорта/РЭ
  characteristics: Characteristic[],
  actions: Action[],                   // ВВ (ТО/ремонт)
  techCards: TechCard[],
  reliability?: Reliability,

  versionsHistory: ChangeEvent[]
}

// Документ (только метаданные!)
DocumentRef {
  id, url, kind: 'passport'|'manual'|'datasheet'|'other',
  filename?, mimeType?, hash?,
  parsedAt?, parserVersion?,
  cache: { textBlobId?, tablesBlobId?, imagesBlobIds? }
}

// Характеристика
Characteristic {
  key, valueRaw,
  valueNormalized: { num?: number, unit?: string, text?: string, enum?: string },
  isPriority: boolean,
  source: Source, confidence: number, lockedByExpert: boolean
}

// Виды воздействий (ТО/ремонт)
Action {
  id, name, kind: 'TO'|'repair'|'inspection'|'diagnostic',
  periodicity?: Periodicity,           // напр. {hours: 4000} или {months: 6}
  description?, source: Source, confidence: number, lockedByExpert: boolean
}
Periodicity = { hours?: number, months?: number, cycles?: number, condition?: string }

// Техкарта
TechCard {
  id, modelId, mode: 'simple'|'advanced',
  components: Component[],             // структура / запчасти
  operations: Operation[],             // последовательность работ
  tmc: TMCItem[],                      // материалы и запчасти (без инструмента)
  sourceDocs: string[]                 // documentIds, на которых построена карта
}
Component { id, code?, name, qty, parentId?, role?: 'spare'|'assembly' }
Operation { id, order, name, duration?, role?, prerequisites?: string[] }
TMCItem    { id, kind: 'material'|'spare', name, code?, qty, unit, source }

// Аналоги (вычисляется, кэшируется)
AnalogMatch {
  modelId, candidateId,
  score,                                 // 0..1
  matched: { class:bool, subclass:bool, charsOverlap: number },
  diffs: CharDiff[]
}

// Надёжность
Reliability {
  mtbf?: number, mttr?: number, failureRate?: number,
  source: 'history'|'analog'|'web'|'expert',
  evidence: { datasetId?: string, analogIds?: string[], urls?: string[] }
}

// Универсальные
Source = { type: 'document'|'web'|'analog'|'manual'|'classifier', ref?: string }
ChangeEvent = { ts, userId, field, before, after, source }
```

## 3. Алгоритм обработки модели (по шагам)

```
1. Импорт модели
   1.1 Из Excel/CSV: rawCode + узел иерархии  (этап 1)
   1.2 Регистрируется EquipmentModel.status = 'draft'

2. Нормализация кода
   2.1 normalize(rawCode) → normalizedCode   (правила п.8.3)
   2.2 Сохранить applied[] правил для аудита (этап 1)

3. Классификация
   3.1 По шаблонам/ключам классификатора → {class, subclass, score}
   3.2 score < 1.0 → пометить 'предложено, требует подтверждения'
   3.3 Эксперт подтверждает → expertConfirmed = true
   3.4 status = 'TOR' если есть norm.code + class + subclass

4. Привязка документа
   4.1 Эксперт указывает URL паспорта/РЭ → DocumentRef
   4.2 Воркер выкачивает (если нужно), извлекает текст/таблицы/картинки → cache
   4.3 Хеш + версия парсера → возможность переразбора

5. Извлечение характеристик
   5.1 Из cache.text/tables → пары key:value
   5.2 normalizeUnits(value) → SI-единица; enum/число/текст
   5.3 Маппинг ключей по aliases приоритетных характеристик класса
   5.4 Сначала приоритетные (порядок из ClassDef.priorityChars), затем остальные
   5.5 Каждое значение: source=document, confidence по парсеру

6. Извлечение видов воздействий (ВВ)
   6.1 Из таблиц регламента ТО / разделов "техническое обслуживание"
   6.2 Из интернета: enrichWeb(model.normalizedCode + class) → кандидаты
   6.3 Объединение по name+periodicity (фуззи), приоритет: документ > интернет
   6.4 Эксперт может удалить/добавить/зафиксировать

7. Аналоги
   7.1 Кандидаты: same class, same subclass, по близости приоритетных характеристик (косинус по нормализованным числам)
   7.2 Топ-N (по умолчанию 5), с CharDiff для UI-сравнения

8. Техкарты
   Простой режим (single-doc):
     8.1 Один документ → автонабор components/operations/tmc
     8.2 Эксперт правит, сохраняет
   Продвинутый режим (multi-doc):
     8.3 Несколько документов выбраны
     8.4 Извлечение по каждому → объединение:
         - components: union по code/name (фуззи)
         - operations: union по name, упорядочение по order/prerequisites
         - tmc: union по code/name, qty = max(qty)
     8.5 Конфликты помечаются для эксперта

9. ТМЦ
   9.1 Из таблиц "материалы/запасные части/комплектация"
   9.2 Фильтр инструментов: blacklist + классификатор ТМЦ (kind ∈ {material, spare})
   9.3 Унификация ед. изм.

10. Надёжность
    10.1 Если есть Excel истории (отказы, наработки) → расчёт MTBF/MTTR/λ
    10.2 Иначе — по аналогам (среднее с весом по score)
    10.3 Иначе — из открытых источников (web), с пометкой confidence
    10.4 Источник всегда отображается в UI

11. Сохранение и версии
    11.1 Каждое изменение → ChangeEvent
    11.2 Снятие "lockedByExpert" — отдельное действие
    11.3 Перезапуск шагов 4–10 — идемпотентен; зафиксированные поля не меняются
```

## 4. Упрощённая версия для демо

Цель — показать сквозной сценарий «модель → ТОР → характеристики → аналоги → ТК → надёжность» без внешних зависимостей и тяжёлых пайплайнов.

### 4.1 Урезка функциональности

| Область | Полная версия | Демо |
|---|---|---|
| Хранилище | Postgres + S3 + Redis | localStorage + JSON-сиды |
| Парсинг документов | PDF/DOCX/Excel/OCR + LLM | Только Excel/CSV; PDF — прикреплённый текст вручную |
| Извлечение характеристик | Парсер таблиц + правила + LLM-fallback | Регулярки по «ключ: значение» из вставленного текста |
| Единицы измерения | Полный SI-конвертер | Базовая таблица (кВт/Вт, мм/м, °C, об/мин, кг) |
| Интернет-обогащение | Поиск + парсер сайтов | Заглушка: справочник «известных кандидатов ВВ» по подклассу |
| Аналоги | pgvector + косинус | Score = совпадение класс/подкласс + Жаккар по приоритетным числовым |
| Техкарты | Простой + продвинутый | Только простой; объединение — заглушка с подсветкой кандидатов |
| ТМЦ | Извлечение из таблиц + фильтр инструмента | Ручной ввод/импорт Excel + чёрный список инструмента |
| Надёжность | 3 источника + комбинирование | Только Excel-история ИЛИ среднее по аналогам |
| Аудит/версии | Полная история + diff | Лог последних 50 действий per-model |

### 4.2 Что добавляем поверх Этапа 1

1. **Карточка модели** (вкладки): «Свойства» · «Документы» · «Характеристики» · «ВВ» · «Аналоги» · «ТК» · «Надёжность».
2. **Документы**: таблица ссылок (url, тип, дата). Кнопка «Вставить распознанный текст» — на демо парсим текстовое поле.
3. **Характеристики**: Excel-подобная таблица. Сначала приоритетные (жирным), затем остальные. Inline-нормализация единиц.
4. **ВВ**: таблица «Наименование · Тип · Периодичность · Источник». Кнопка «Дополнить из справочника» (заглушка интернета).
5. **Аналоги**: список топ-5 с дельтами по приоритетным характеристикам.
6. **ТК (простой режим)**: три таблицы — Компоненты / Операции / ТМЦ — с импортом из Excel.
7. **Надёжность**: импорт Excel истории отказов → автоподсчёт MTBF/MTTR; либо «по аналогам» с пометкой источника.

### 4.3 Сквозной демо-сценарий (5 минут)

```
1. Импорт иерархии и моделей (этап 1, готово)
2. «Нормализовать» + «Классифицировать» → 19 моделей становятся ТОР (готово)
3. Открыть АИР80А4 → вкладка «Документы» → вставить URL паспорта
4. Вставить распознанный текст РЭ → парсер выдаёт характеристики
   Приоритетные (мощность, напряжение, частота, IP) — сверху
5. Вкладка «ВВ» → авто-наполнение по подклассу (демо-справочник)
6. Вкладка «Аналоги» → видим АИР100,5L4 c diff по мощности
7. Вкладка «ТК» (простой) → импорт Excel со списками
8. Вкладка «Надёжность» → импорт истории отказов → MTBF посчитан
```

### 4.4 Технологический стек демо

- Frontend: текущий Vite + React + TS (продолжение Этапа 1).
- Состояние: zustand; вся БД — в браузере (IndexedDB через `idb-keyval`).
- Парсинг: `xlsx` (готово) + простой regex-движок для текста; PDF/DOCX — на позже.
- Без бэкенда. Бэкенд добавим, когда демо подтвердится.
